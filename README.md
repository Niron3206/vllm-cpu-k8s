# vLLM на CPU в Kubernetes

Инференс `RedHatAI/Qwen2.5-1.5B-Instruct-quantized.w8a8` (INT8 W8A8) на vLLM 0.32.0 в minikube, только CPU. Образ rootless, зависимости запинены с хешами, промпты и ответы в логи не попадают, веса кешируются на PVC, токены лежат в Secret, параметры vLLM задаются через ConfigMap. Плюс все доп. три задания: kustomize, загрузчик весов в отдельном initContainer, нагрузочный тест.

## Что где лежит

| Путь | Что там |
|---|---|
| `docker/vllm/` | Dockerfile основного образа и `requirements.txt` (все пакеты с хешами) |
| `docker/downloader/` | лёгкий образ initContainer и `download_model.py` |
| `plugin/` | `vllm_guard`: логирование без текста запросов, Bearer-токен на всех маршрутах, тесты |
| `k8s/` | манифесты для `kubectl apply -k k8s`, в `config/` всё, что попадает в ConfigMap |
| `bench/` | оверлей с Job для нагрузочного теста, сценарии и результаты |
| `scripts/` | `lock.sh` (пересборка пинов), `smoke.sh` (проверка деплоя), `bench.sh` |

## Запуск

Проверялось всё на WSL2 (Ubuntu 24.04) с Docker Desktop, minikube 1.39 (Kubernetes 1.37), kubectl 1.37. Процессор на 8 ядер и 16 потоков, AVX2 есть, AVX-512 нет.

Под просит 10 CPU и 9 ГБ памяти, а `VLLM_CPU_OMP_THREADS_BIND` в `k8s/config/vllm.env` привязывает потоки к логическим CPU 0, 2, ..., 14 (по одному на физическое ядро, SMT-пары идут подряд). **На другой машине поправьте `resources` в `k8s/deployment.yaml` и привязку по выводу `lscpu -e` или поставьте `auto`.**

```bash
minikube start --driver=docker --container-runtime=docker --cpus=12 --memory=11g --disk-size=60g

# собираем образы сразу в докере minikube, тогда их не надо никуда загружать
eval $(minikube docker-env)
docker build -f docker/vllm/Dockerfile --target test .     # тесты плагина
docker build -f docker/vllm/Dockerfile --target runtime -t vllm-cpu:0.32.0 .
docker build -f docker/downloader/Dockerfile -t model-downloader:0.1.0 .

cp k8s/secrets.env.example k8s/secrets.env
sed -i "s/^VLLM_API_KEY=.*/VLLM_API_KEY=$(openssl rand -hex 32)/" k8s/secrets.env
# HF_TOKEN нужен только для gated-моделей

kubectl apply -k k8s
kubectl -n llm rollout status deploy/vllm --timeout=15m
./scripts/smoke.sh
```

При первом старте initContainer скачивает 2.1 ГБ весов, это минута-две. Сам vLLM поднимается примерно за 40 секунд. Первый запрос на чистом томе идёт около двух минут: triton-cpu компилирует ядра. Скомпилированное сохраняется на PVC `vllm-cache`, после рестарта первый ответ приходит за пару секунд.

Запрос руками:

```bash
kubectl -n llm port-forward svc/vllm 8000:8000 &
TOKEN=$(grep '^VLLM_API_KEY=' k8s/secrets.env | cut -d= -f2-)
curl -s http://127.0.0.1:8000/v1/chat/completions \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"model": "qwen2.5-1.5b-instruct", "max_tokens": 64,
       "messages": [{"role": "user", "content": "Что такое PVC в Kubernetes?"}]}'
```

`smoke.sh` проверяет, что без токена отвечает только `/health`, модель отвечает с токеном, текста запроса и ответа нет в логах, строка о запросе есть, а процесс работает от uid 10001.

## Настройки

Всё лежит в `k8s/config/` и собирается в ConfigMap генератором kustomize:

- `serve.yaml`: аргументы `vllm serve` (`max-num-seqs`, `max-model-len`, размер KV-кеша и т.д.);
- `vllm.env`: модель и её ревизия, путь на томе, имя для API, привязка потоков OpenMP;
- `logging.json`: конфиг логов vLLM и uvicorn.

После правки выполните `kubectl apply -k k8s`. В имени ConfigMap есть хеш содержимого, поэтому Deployment увидит новое имя и сам перезапустит под. С Secret так же. Пересобирать образ не нужно.

Другую модель подключают через `MODEL_ID`, `MODEL_REVISION` и `MODEL_DIR` в `vllm.env`. Её скачает initContainer, а старые веса останутся на томе.

## Как устроено

### Образ

На PyPI у vLLM только CUDA-колёса, CPU-сборка лежит в GitHub Release. Колесо 0.32.0 собрано под glibc 2.39, поэтому базовый образ `python:3.12-slim-trixie` (в bookworm glibc 2.36). В колесе есть `_C_AVX2` и `_C_AVX512`, нужное выбирается при старте.

`requirements.txt` генерирует `scripts/lock.sh`: `uv pip compile` с `--generate-hashes` в контейнере, чтобы результат не зависел от хоста. В образ пакеты ставятся с `--require-hashes --no-deps`, так что подтянуть что-то незапиненное нельзя. Базовые образы и uv тоже закреплены по digest.

В рантайме нужен `g++`. Ядра triton-cpu  компилируются при первом запросе, и без компилятора сервер падает даже с `--enforce-eager`. Образ весит 3.8 ГБ, из них около 260 МБ занимает компилятор.

Процесс работает от uid 10001, в поде корневая ФС только на чтение. Байткод компилируется при сборке. Телеметрия vLLM выключена (`VLLM_NO_USAGE_STATS`), в Hugging Face основной контейнер не ходит (`HF_HUB_OFFLINE=1`).

### Логи без промптов

Где vLLM 0.32 пишет текст запросов и ответов:

- `RequestLogger` на DEBUG пишет промпт и всё тело запроса, а с `--enable-log-outputs` пишет сгенерированный текст уже на INFO;
- middleware `log_response` пишет тела ответов, если задана `VLLM_DEBUG_LOG_API_SERVER_RESPONSE`;
- на DEBUG текст пишут tool-парсеры, `renderers/chat_utils`.

Защита в два слоя, оба в `plugin/vllm_guard`:

1. `request_log`: плагин, подключённый через entry point `vllm.general_plugins`, vLLM загружает его сам при старте. Он подменяет методы `RequestLogger`: остаются id запроса и счётчики токенов. Если в новой версии vLLM поменяются сигнатуры этих методов, сервер не стартует. Лучше упасть, чем молча вернуть запись промптов.
2. `log_filter` висит на хендлере в `logging.json` и отбрасывает записи модулей, которые пишут текст: `log_response` всегда, а tool-парсеры, рендереры и обработчики API ниже уровня INFO. DEBUG для остального движка работает.

Что остаётся в логе:

```
INFO [request_log.py:24] request chatcmpl-bc738c73a0562d02: prompt_tokens=46 max_tokens=32
INFO [request_log.py:37] response chatcmpl-bc738c73a0562d02: output_tokens=15 finish_reason=stop
INFO [httptools_impl.py:482] 127.0.0.1:37240 - "POST /v1/chat/completions HTTP/1.1" 200
```

Последняя строка взята из access-лога uvicorn. vLLM передаёт uvicorn тот же конфиг логов, поэтому в `logging.json` прописан и логгер `uvicorn`, иначе access-лог пропадает.

### Токен API

Встроенный `--api-key` (`VLLM_API_KEY`) проверяет только пути с префиксами `/v1`, `/v2`, `/inference`, `/cohere`. Маршрут `/invocations` (для SageMaker) регистрируется всегда и отдаёт ту же генерацию без токена, об этом написано в справке к флагу. Поэтому подключён свой middleware `vllm_guard.auth.BearerAuth` (`--middleware` в `serve.yaml`): токен нужен везде, кроме `/health`. Встроенная проверка тоже остаётся включённой.

### Веса и кеш

initContainer `model-downloader` (alpine, 80 МБ, uid 10001) проверяет маркер `.complete` с `MODEL_ID@MODEL_REVISION`. Если маркер на месте, контейнер сразу выходит, не трогая сеть. Если нет, скачивает snapshot нужной ревизии через `huggingface_hub` и записывает маркер. HF-токен получает только он. Основной контейнер монтирует том с весами только на чтение.

Повторный запуск загрузчика с `docker run --network none` на заполненном томе проходит за полсекунды.

### Под

- namespace с Pod Security Admission `restricted`;
- `runAsNonRoot`, `drop: [ALL]`, `allowPrivilegeEscalation: false`, `seccompProfile: RuntimeDefault`, токен ServiceAccount не монтируется;
- `enableServiceLinks: false`, потому что Service с именем `vllm` иначе добавляет в окружение `VLLM_PORT=tcp://…`, и vLLM падает, приняв его за свою настройку;
- `SYS_NICE` и `seccomp: Unconfined`, которые предлагает документация vLLM для CPU, нужны для привязки памяти к NUMA-нодам, на одной ноде от них толку нет;
- `strategy: Recreate`: том RWO, и два пода по 9 ГБ на ноду не помещаются.

### Почему W8A8 и eager

Пробовалось варианты на одиночном запросе:

| Вариант | Старт | Декод | Префилл |
|---|---|---|---|
| W8A8, `torch.compile` | 138 с | 3.9 ток/с | 225 ток/с |
| W8A8, eager | 41 с | 3.7 ток/с | 220 ток/с |
| bf16 без квантизации, eager | н/д | 7.7 ток/с | 31 ток/с |

`torch.compile` здесь ничего не ускоряет, только удлиняет старт. Поэтому в `serve.yaml` стоит `enforce-eager: true`. Без квантизации декод одного запроса вдвое быстрее, зато префилл в 7 раз медленнее. Под нагрузкой это потолок около 30 ток/с на весь сервер, поэтому выбран W8A8.

## Нагрузочное тестирование

```bash
./scripts/bench.sh   # пересоздаёт Job из bench/, ждёт его, пишет bench/results/<время>.{log,md}
```

Job использует тот же образ и `vllm bench serve`. Промпты случайные заданной длины, ответ всегда 64 токена (`--ignore-eos`). Перед каждым сценарием идёт прогрев с той же конкурентностью. triton-cpu компилирует ядра под каждую новую форму батча, и без прогрева компиляция попала бы в замер. Сценарии перечислены в `bench/scenarios.txt`. Сервер работает на 8 физических ядрах, по потоку на ядро, лимит пода 10 CPU.

Результаты (`bench/results/baseline.md`):

| Сценарий | Вход / выход, ток. | Одновр. | TTFT p50 / p99, с | TPOT p50, мс | Latency p50 / p99, с | Запросов/с | Выход, ток/с | Всего, ток/с |
|---|---|---|---|---|---|---|---|---|
| short-c1 | 128 / 64 | 1 | 1.85 / 1.90 | 272 | 19.0 / 19.2 | 0.05 | 3.4 | 10.1 |
| short-c8 | 128 / 64 | 8 | 6.85 / 7.45 | 1612 | 108.2 / 110.9 | 0.07 | 4.7 | 14.1 |
| short-c32 | 128 / 64 | 32 | 12.83 / 17.43 | 1923 | 133.2 / 136.0 | 0.24 | 15.2 | 45.6 |
| long-c1 | 4096 / 64 | 1 | 17.45 / 17.77 | 285 | 35.5 / 35.8 | 0.03 | 2.0 | 131.5 |
| long-c4 | 4096 / 64 | 4 | 12.39 / 69.91 | 898 | 91.9 / 124.6 | 0.04 | 2.8 | 179.0 |

TTFT считается до первого токена, TPOT на каждый следующий токен, Latency охватывает весь запрос. В "Всего" входят и токены промпта.

Цифры довольно скромные, и причина нашлась в профиле (py-spy). Т.к. больше половины времени уходит в `simple_gemm_s8s8s32` из oneDNN, а это референсная реализация без JIT. У модели симметричные int8-активации, и на AVX2 без VNNI oneDNN уходит в медленный путь. Быстрый int8-путь vLLM (`int8_scaled_mm_with_quant`) собран только под AVX-512. Как время матмула зависит от числа строк, показывает `bench/int8_matmul.py` (`bench/results/int8_matmul.txt`, матрица MLP-слоя модели):

| Строк в батче | 1 | 8 | 16 | 32 | 128 | 2048 |
|---|---|---|---|---|---|---|
| мс на матмул | 1.7 | 14.7 | 13.8 | 13.4 | 16.7 | 61.8 |
| мкс на строку | 1724 | 1835 | 860 | 418 | 131 | 30 |

До 8 строк каждая строка заново проходит по весам, и время растёт линейно. Примерно с 16 строк включается блочный GEMM, и до 128 время почти не меняется. Отсюда слабый выигрыш на short-c8. Шаг декода в 6 раз дороже, чем при одном запросе, а токенов за шаг всего в 8 раз больше. Асимметричные активации картину не меняют, это проверено тем же скриптом.

### Что крутить для throughput

**А. Много запросов с короткими промптами.** Узкое место здесь в декоде, и выгоднее всего держать батч большим.

- `max-num-seqs` задаёт, сколько последовательностей идёт в одном шаге. Замер со 128 одновременными запросами (`bench/results/exp-a-*`): при 32 выход 15.4 ток/с и TTFT p50 208 с, при 128 уже 35.6 ток/с и 34 с. Шаг стал дороже в 1.5 раза, а токенов за шаг вчетверо больше. Поэтому в `serve.yaml` стоит 128.
- `max-num-batched-tokens` не должен быть меньше `max-num-seqs`, иначе декод всех последовательностей не уместится в шаг.
- KV-кеш (`kv-cache-memory-bytes`) должен вмещать `max-num-seqs` умноженную на длину контекста, иначе vLLM начнёт вытеснять запросы.
- Если у запросов общий системный промпт, помогает prefix caching (в vLLM включён по умолчанию).
- Потоки OpenMP: по одному на физическое ядро, одно-два ядра оставить API-серверу. На многосокетных серверах лучше ставить отдельную реплику (или DP-ранг) на каждую NUMA-ноду.

**Б. Запросов мало, но контекст огромный.** Узкое место в префилле: здесь он около 230 ток/с, и на 4096 токенов уходит 17 секунд.

- Первым делом prefix caching: если контекст повторяется (одни и те же документы в RAG, длинная инструкция), префилл пересчитывается только для новой части.
- `max-num-batched-tokens` ограничивает размер куска префилла за шаг. Документация советует его увеличивать, но здесь 8192 вместо 2048 (`bench/results/exp-b-*`) дал 143 ток/с вместо 179, и TPOT соседних запросов вырос на 29%: длинный шаг префилла задерживает их декод. Хотя в изолированном матмуле крупный кусок выигрывает около 8% (27.7 против 30.2 мкс на строку), в сервере 2048 оказался лучше.
- `max-model-len` и KV-кеш должны быть рассчитаны на длинный контекст, `max-num-seqs` для такого сценария можно уменьшить.
- Сильнее всего здесь помогает железо: на CPU с AVX-512 VNNI или AMX vLLM использует быстрые int8- и bf16-ядра. Там же доступен FP8 KV-кеш, в который помещается вдвое больше контекста. На нескольких NUMA-нодах помогает tensor parallel по нодам.

## Чего нет и что сделал бы я иначе

- NetworkPolicy. Ограничить исходящий трафик пода нельзя, пока init-контейнеру нужен Hugging Face. В проде веса лучше класть в своё хранилище заранее.
- Секреты в `secrets.env` подходят для стенда. В кластере я бы взял External Secrets или Vault.
- apt-пакеты в образе не запинены по версиям. Старые версии исчезают из зеркал Debian. Для полной повторяемости можно ставить из snapshot.debian.org.
- Первый деплой на чистый том платит за JIT-компиляцию ядер. Можно прогревать их отдельным запросом перед тем, как пускать трафик.
